# Data Model: Architecture Decision Lab

## Conventions

- Application identifiers are UUIDv7-compatible strings generated by the application.
- Timestamps are timezone-aware UTC values named `created_at`, `updated_at`, or terminal-state
  timestamps.
- Mutable records use integer optimistic-lock versions where concurrent updates are possible.
- Published versions, run inputs, raw outputs, and evaluation submissions are immutable.
- JSON fields are validated by versioned Pydantic schemas before persistence.
- Content hashes use SHA-256 over canonical UTF-8 or file bytes.

## DecisionCategory

Enum values:

- `sql_vs_nosql`
- `sync_vs_async`
- `modular_monolith_vs_microservices`
- `containers_vs_serverless_vs_traditional`
- `unsupported`

A scenario that matches several supported categories stores each matched category in deterministic
enum order. A scenario that matches none stores exactly `[unsupported]`; `unsupported` cannot be
combined with a supported value.

## DecisionScenario

Represents stable scenario identity.

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `title` | string | Required, 3–200 characters |
| `language` | string | Required; initial allowed value `pt-BR` |
| `current_revision_number` | integer | Required, greater than or equal to 1 |
| `created_at` | timestamp | Required, immutable |
| `updated_at` | timestamp | Required |

Relationships: one scenario has one or more `ScenarioRevision` records.

## ScenarioRevision

Immutable input snapshot used by analysis runs.

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `scenario_id` | UUID | Required foreign key |
| `revision_number` | integer | Required, greater than or equal to 1; unique with `scenario_id` |
| `problem` | text | Required, 20–20,000 characters |
| `facts` | list[string] | 0–50 items; each item 1–2,000 characters |
| `constraints` | list[string] | 0–50 items; each item 1–2,000 characters |
| `desired_qualities` | list[string] | 0–20 items; each item 1–500 characters |
| `candidate_alternatives` | list[string] | 0–20 items; each item 1–500 characters |
| `clarification_answers` | list[object] | Question, answer, and source run identifier |
| `categories` | list[DecisionCategory] | At least one value after classification |
| `content_hash` | SHA-256 | Required; unique with `scenario_id` |
| `created_at` | timestamp | Required, immutable |

Invariant: adding clarification answers creates a new revision; an existing revision is never
edited. Scenario classification completes before persistence. The canonical hash payload contains
`problem`, `facts`, `constraints`, `desired_qualities`, `candidate_alternatives`,
`clarification_answers`, and `categories`; strings are trimmed, object keys are sorted, list order
is preserved, and database IDs, revision numbers, titles, and timestamps are excluded. The total
UTF-8 request body is limited to 100 KiB before validation.

### ClarificationQuestion and ClarificationAnswer

`ClarificationQuestion` is an immutable view of an `ADRDraft.unresolved_questions` item plus its
provenance. It is resolved server-side from persisted run evidence rather than accepted as client
prose.

| Field | Type | Constraints |
| --- | --- | --- |
| `question_id` | string | Required; unique within the source ADR |
| `question` | string | Required authoritative snapshot, 1–2,000 characters |
| `impact` | string | Required explanation of why the answer matters, 1–2,000 characters |
| `source_run_id` | UUID | Required terminal run in `needs_clarification` |

`ClarificationAnswer` embeds that question snapshot and adds:

| Field | Type | Constraints |
| --- | --- | --- |
| `answer` | string | Required after trimming, 1–5,000 characters |

A revision request contains one to three answers with distinct `question_id` values. Every source
run belongs to the requested base revision and scenario, owns a stored provisional ADR, and exposes
the referenced question. Stored answer order follows request order. Revisions append answer
snapshots to inherited prior answers; an existing question cannot be answered twice in the same
resulting revision.

Creating revision `N + 1` conditionally advances `DecisionScenario.current_revision_number` only
when it is still `N`. The head update and revision insert are atomic. A stale base changes neither
row and returns `409 stale_revision`; previous revisions, runs, ADRs, artifacts, and findings are
immutable.

## RetrievalSnapshot

Immutable context retrieved once and reused across comparable strategies.

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `provider` | string | Required; initially `knowledge_hub` or `fixture` |
| `provider_version` | string | Required |
| `query` | text | Required, 1–10,000 characters |
| `filters` | object | Validated category, tag, project, limit, and score filters |
| `embedding_model` | string | Required for live retrieval |
| `embedding_version` | string | Required for live retrieval |
| `content_hash` | SHA-256 | Required, unique for canonical ordered chunks and metadata |
| `artifact_id` | UUID | Exact snapshot artifact |
| `created_at` | timestamp | Required |

The canonical artifact is a closed JSON document with `schema_version`, provider identity/version,
query, normalized filters, embedding identity, and ordered `RetrievalChunkSnapshot` entries. Each
chunk contains source ID, chunk ID, title, URI, structured location, exact content, finite score,
ordered match reasons, one-based unique rank, and its own content hash. Provider order is
significant and is never re-sorted.

`content_hash` is calculated from that complete canonical document. It excludes snapshot ID,
artifact ID/path, and `created_at`; all request, provider, embedding, ordering, and chunk fields are
included. An equal hash must resolve to byte-identical canonical artifact content or fail an
integrity check. The unique hash permits safe create-or-reuse after concurrent retrieval.

The artifact bytes are published before a single metadata transaction inserts `Artifact`,
`RetrievalSnapshot`, and `ArtifactReference(owner_type="retrieval_snapshot")`. A database rollback
may leave only an unreferenced physical object for conservative reconciliation; committed snapshot
metadata must never point to missing bytes.

## AnalysisRun

Immutable execution record with controlled state transitions.

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `scenario_revision_id` | UUID | Required foreign key |
| `strategy_id` / `strategy_version` | string | Required composite reference |
| `retrieval_snapshot_id` | UUID? | Required when strategy requires retrieval |
| `experiment_id` | UUID? | Optional grouping reference |
| `scenario_content_hash` | SHA-256 | Frozen input identity |
| `strategy_configuration_hash` | SHA-256 | Model, revision, adapter, prompt, and strategy identity |
| `generation_config_hash` | SHA-256 | Frozen decoding configuration identity |
| `status` | enum | See state machine below |
| `stage` | string | Sanitized current progress stage |
| `progress_percent` | integer? | 0–100 when measurable |
| `progress_sequence` | integer | Non-negative; increases for every persisted stage snapshot |
| `raw_output_artifact_id` | UUID? | Preserve first model output when produced |
| `repaired_output_artifact_id` | UUID? | Preserve the single repair output when attempted |
| `validation_attempts` | list[OutputValidationAttempt] | Immutable summaries for original and optional repair |
| `adr_draft_id` | UUID? | Set only after valid structured output |
| `failure_code` | string? | Stable machine-readable code |
| `failure_detail` | string? | Sanitized, maximum 2,000 characters |
| `input_tokens` / `output_tokens` | integer? | Non-negative |
| `latency_ms` | integer? | Non-negative |
| `peak_vram_mb` | integer? | Non-negative |
| `created_at`, `updated_at`, `started_at`, `finished_at` | timestamp | Terminal runs require `finished_at` |

`OutputValidationAttempt` contains `attempt` (`original` or `repaired`), the referenced output
artifact ID, parse success, schema version when detected, and ordered findings. Each finding has a
stable `code`, JSON-style `path`, severity (`error` or `warning`), and sanitized message.

States:

```text
pending -> waiting_resources -> running
running -> completed | needs_clarification | invalid_output | failed | cancelled | interrupted
pending | waiting_resources -> cancelled
pending | waiting_resources -> failed  # dispatch or resource-preflight failure
pending | waiting_resources | running -> interrupted  # startup recovery only
```

Terminal runs cannot transition again. Retrying creates a new run. `completed` requires a valid
`proposed` ADR; `needs_clarification` requires a valid `provisional` ADR with one to three
questions; `invalid_output` requires original validation evidence, optional repair evidence, and
no ADR. Startup converts every orphaned non-terminal run to `interrupted` because the in-memory
executor queue is not durable.

## ADRDraft

Structured, schema-versioned result.

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `analysis_run_id` | UUID | Required, unique foreign key |
| `schema_version` | string | Required |
| `title` | string | Required, 3–200 characters |
| `status` | enum | Generated output is `provisional` or `proposed`; human lifecycle statuses are reserved |
| `context` | list[string] | At least one item |
| `facts` | list[string] | May be empty only for provisional output |
| `assumptions` | list[object] | Statement, impact, confidence |
| `unresolved_questions` | list[object] | Maximum three per clarification round |
| `constraints` | list[string] | At least one for conclusive output |
| `alternatives` | list[object] | At least two viable alternatives for conclusive output |
| `decision` | text? | Required unless clarification is needed |
| `rationale` | list[object] | Claim linked to fact, assumption, or reference identifiers |
| `positive_consequences` | list[string] | At least one for conclusive output |
| `negative_consequences` | list[string] | At least one for conclusive output |
| `risks` | list[object] | Description, likelihood, impact, mitigation |
| `review_triggers` | list[object] | At least one for conclusive output; metric, operator, threshold, unit |
| `confidence` | decimal | 0.0–1.0 |
| `reference_ids` | list[string] | Identifiers from retrieval snapshot |
| `created_at` | timestamp | Required |

Closed nested value objects:

- `Assumption`: `id`, statement, impact, and confidence from 0.0 through 1.0.
- `UnresolvedQuestion`: `id`, question, and why/impact text; at most three.
- `Alternative`: `id`, name, summary, viability, rejection reason when not viable, benefits,
  drawbacks, and linked constraint identifiers.
- `RationaleLink`: claim plus a non-empty evidence kind (`fact`, `assumption`, or `reference`) and
  evidence identifier.
- `Risk`: description, likelihood (`low`, `medium`, `high`), impact (`low`, `medium`, `high`), and
  mitigation.
- `ReviewTrigger`: metric, operator (`gt`, `gte`, `lt`, `lte`, `eq`), finite numeric threshold,
  and unit.

Invariant: application validation and benchmark validation call the same evaluator functions. A
`proposed` ADR is conclusive and therefore requires a decision, at least one constraint, at least
two viable alternatives, positive and negative consequences, rationale links, and at least one
measurable review trigger. A `provisional` ADR may omit a decision only when it contains one to
three unresolved questions and explicit assumptions. Renderers serialize only supplied validated
content and never synthesize missing sections.

Facts and constraints use stable zero-based identifiers derived from their position in the
validated ADR: `fact:0`, `fact:1`, and `constraint:0`, for example. `RationaleLink.evidence_id`
uses a `fact:N` identifier for fact evidence, an `Assumption.id` for assumption evidence, or a
retrieval `reference_id` for reference evidence. `Alternative.constraint_ids` uses only existing
`constraint:N` identifiers. Renderers preserve list order, so these identifiers are stable for the
immutable draft.

## BlindComparison and EvaluationResult

`BlindComparison` contains an ID, immutable rubric version ID, creation timestamp, and nullable
`current_evaluation_id`. It accepts at least two distinct completed runs with stored ADRs from the
same scenario revision. RAG candidates in one comparison use the same retrieval snapshot and
generation configuration.

`ComparisonCandidate` is a child row containing comparison ID, opaque randomized label, run ID,
and frozen ADR artifact/content hash. Unique constraints cover `(comparison_id, label)` and
`(comparison_id, run_id)`. Labels do not encode insertion order, run, strategy, or model identity.
The normal ADR/run representation is never serialized from this row before reveal.

`BlindedCandidate` is the public pre-reveal projection: anonymous label plus reviewable ADR content
only. It omits ADR ID, analysis run ID, strategy/model/prompt/adapter identity, retrieval identity,
artifact identity, timestamps, latency, and resource measurements. `BlindComparison` also projects
the immutable rubric dimensions, anchors, and score bounds so clients do not hard-code them.

`EvaluationResult` fields are:

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `comparison_id` | UUID | Required foreign key |
| `rubric_version_id` | UUID | Must equal comparison rubric |
| `evaluator_id` | string | Pseudonymous, 1–200 characters |
| `evaluator_type` | enum | `human`, `llm_assisted`, `deterministic` |
| `judge_model_identity` | object? | Required only when an external judge model is used |
| `scores` | object | Exact label × rubric-dimension integer matrix within declared bounds |
| `preference` | string | One comparison label or `tie` |
| `notes` | string? | At most 5,000 characters |
| `supersedes_evaluation_id` | UUID? | Current result of the same comparison when correcting |
| `submitted_at` | timestamp | Required |

The first valid submission sets `current_evaluation_id` in the same transaction. A correction is a
new immutable row whose `supersedes_evaluation_id` equals the current head; the head then advances
atomically. Duplicate initial submissions, stale parents, cross-comparison parents, cycles, and
score matrices with missing/extra labels or dimensions are rejected. Reveal is permitted only when
`current_evaluation_id` is non-null; evaluation history is never overwritten.

## DatasetVersion and DatasetMembership

`DatasetVersion` states are `building`, `validating`, `published`, and `rejected`. Publication
freezes its manifest hash. `DatasetMembership` assigns an example to exactly one of `train`,
`validation`, or `evaluation`, with a lineage group identifier used to prevent derived-family
leakage across partitions.

Invariant: no content hash, semantic duplicate above the configured review threshold, or lineage
group may cross from train/validation into fixed evaluation without explicit dataset rejection.

## ArtifactReference

| Field | Type | Constraints |
| --- | --- | --- |
| `artifact_id` | UUID | Foreign key to `Artifact`; part of primary key |
| `owner_type` | string | Stable, registered owner kind; part of primary key |
| `owner_id` | UUID | Owning entity identity; part of primary key |
| `created_at` | timestamp | Required, timezone-aware UTC |

Artifact-owning services create or remove references in the same unit of work as their owning
metadata. The artifact service treats unknown owner types as invalid and refuses physical deletion
while any reference exists. The registry allows the foundational artifact service to enforce safe
deletion before later owner tables are introduced.

## ArtifactPruneAudit

| Field | Type | Constraints |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `operation_id` | UUID | Groups one confirmed prune invocation |
| `artifact_id` | UUID | Identity selected from the catalog; retained as audit data after deletion |
| `artifact_kind` | enum | Snapshot of the deleted artifact kind |
| `relative_path` | string | Validated catalog path at selection time |
| `sha256` | string | 64 lowercase hexadecimal characters |
| `reason` | enum | `unreferenced_prunable`, `expired_temporary`, `missing_bytes` |
| `reclaimed_bytes` | integer | Non-negative; zero when bytes were already absent |
| `pruned_at` | timestamp | Required, timezone-aware UTC |

Rows are append-only. One artifact may appear at most once in a successful prune operation. A
failed filesystem deletion creates no success audit and leaves the artifact catalog row available
for retry. Audit insertion and removal of the successfully deleted catalog row commit together;
the command reports any filesystem/database boundary failure without claiming its bytes.

## DatabaseBackupManifest

`DatabaseBackupManifest` is a versioned canonical JSON sidecar, not a SQLite table, because its
purpose is to verify a database independently of the source database. It contains
`manifest_version`, `created_at`, `schema_revision`, `database_size_bytes`, `database_sha256`, and
`application_version`. The hash covers the finalized backup bytes, never the manifest itself.
Restore validation rejects a size/hash mismatch, a failed SQLite integrity check, or a schema
revision newer than the validating application. Phase 8 restores only to an isolated temporary
path and never replaces the configured live database.

## Indexes

- Scenario revision unique indexes on `(scenario_id, revision_number)` and
  `(scenario_id, content_hash)`.
- Run indexes on `(status, created_at)`, `experiment_id`, and `scenario_revision_id`.
- Experiment index on `(status, created_at)`.
- Dataset membership indexes on `(dataset_version_id, split)` and `lineage_group_id`.
- Artifact unique index on `(sha256, kind)` and index on retention.
- Artifact-reference index on `(artifact_id, owner_type)`.
- Artifact-prune-audit indexes on `(operation_id, pruned_at)` and `artifact_id`.
- Retrieval snapshot unique index on `content_hash` and indexes on `(provider, created_at)` and
  `artifact_id`.
- Rubric version unique indexes on `(name, version)` and `content_hash`.
- Comparison-candidate unique indexes on `(comparison_id, label)` and
  `(comparison_id, run_id)`.
- Evaluation indexes on `(comparison_id, submitted_at)` and `rubric_version_id`, plus a unique
  nullable `supersedes_evaluation_id` so one result cannot fork into two direct corrections.

## Retention and Recovery

- Public dataset manifests and schemas are permanent in Git history.
- Experiment metadata is retained until explicit deletion and included in daily optional backup.
- Raw outputs and retrieval snapshots referenced by published reports are `keep`.
- Intermediate checkpoints default to `prunable` and count toward the 50 GB budget.
- The application warns at 40 GB and blocks new training before free disk would fall below a safe
  configured reserve.
